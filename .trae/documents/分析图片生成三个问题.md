1. **问题1修复**：`iter_sse_payloads` 看门狗加固 — 防止 SSE 流读取无限阻塞导致超时失效

## 修复1：`iter_sse_payloads` 看门狗加固

### 问题根因

当前看门狗用 `threading.Timer` 在超时后调用 `response.close()` 尝试中断 `iter_lines()` 阻塞，但 `curl_cffi` 的 `iter_lines()` 底层可能在 C 层阻塞读取，`response.close()` 在另一线程调用可能无法可靠中断。一旦看门狗失效，SSE 流读取会**无限阻塞**，deadline 检查在循环顶部无法介入，导致任务运行远超 300 秒上限（如 4170 秒）。

### 当前实现

**文件**：[helper.py:233-276](file:///d:/GithubProject/chatgpt2api/utils/helper.py#L233-L276)

```python
def iter_sse_payloads(response, stream_timeout_secs=None):
    timed_out = threading.Event()
    watchdog = None
    if stream_timeout_secs and stream_timeout_secs > 0:
        def _force_close():
            timed_out.set()
            try:
                response.close()
            except Exception:
                pass
        watchdog = threading.Timer(stream_timeout_secs, _force_close)
        watchdog.daemon = True
        watchdog.start()
    try:
        for raw_line in response.iter_lines():  # ← 可能无限阻塞
            ...
    except Exception as exc:
        if timed_out.is_set():
            raise SSEStreamTimeoutError(...)
        raise
    finally:
        if watchdog is not None:
            watchdog.cancel()
```

### 修复方案

**核心思路**：看门狗触发后，不仅 `response.close()`，还需关闭底层 session 释放连接；同时在读取循环中增加超时状态检查作为双保险。

#### 改动文件：`utils/helper.py`

1. **`iter_sse_payloads` 增加 `session` 参数**：
   - 看门狗回调中，先 `response.close()`，再尝试 `session.close()` 强制释放底层连接池
   - 如果 `session` 不可用（未传入），仅 `response.close()`

2. **看门狗回调加固**：
   ```python
   def _force_close():
       timed_out.set()
       logger.warning({"event": "sse_watchdog_triggered", "stream_timeout_secs": stream_timeout_secs})
       try:
           response.close()
       except Exception:
           pass
       if session is not None:
           try:
               session.close()  # 强制释放底层连接，中断 curl 阻塞
           except Exception:
               pass
   ```

3. **读取循环增加超时检查**（双保险）：
   - 在 `for raw_line in response.iter_lines()` 循环体内，每次迭代检查 `timed_out.is_set()`
   - 如果已超时，立即 break 并抛出 `SSEStreamTimeoutError`
   - 注意：这只能处理 `iter_lines()` 有返回的情况，无法处理完全卡死的情况，因此 session.close() 是主防线

#### 改动文件：`services/openai_backend_api.py`

4. **调用 `iter_sse_payloads` 时传入 session**：

   需要修改所有调用 `iter_sse_payloads` 的位置，传入 `self.session`：

   - [openai_backend_api.py:2667](file:///d:/GithubProject/chatgpt2api/services/openai_backend_api.py#L2667) `_stream_picture_conversation` 中：
     ```python
     yield from iter_sse_payloads(response, stream_timeout_secs=timeout_secs, session=self.session)
     ```

   - [openai_backend_api.py:2636](file:///d:/GithubProject/chatgpt2api/services/openai_backend_api.py#L2636) `stream_conversation` 中（非 picture_v2 分支的 SSE 流）：
     ```python
     yield from iter_sse_payloads(response, stream_timeout_secs=timeout_secs or 300, session=self.session)
     ```

   - 搜索确认是否有其他调用 `iter_sse_payloads` 的位置，一并修改。

#### 改动文件：`utils/helper.py`（`iter_sse_payloads` 签名）

5. **函数签名变更**：
   ```python

       response: requests.Response,
       stream_timeout_secs: float | None = None,
       session = None,  # 新增：用于看门狗强制关闭
   ) -> Iterator[str]:
   ```

### 验证

- 模拟 `iter_lines()` 阻塞不返回的场景，验证看门狗触发后能在短时间内（几秒内）中断并抛出 `SSEStreamTimeoutError`
- 确认正常 SSE 流读取不受影响（看门狗在正常完成后 cancel）
- 确认 `session.close()` 后的后续请求能正常新建 session（`OpenAIBackendAPI.close()` 会处理）

## 修复2：参考图上传复用

### 问题根因

多图生成时，每张图独立调用 `_generate_single_image`，每次都重新执行完整流程包括 `_upload_image`。在重试场景下（TLS 错误、连接超时等同账号重试），同一账号的参考图被重复上传。编辑模式（图生图）下 N 张图 × M 张参考图 = 3×N×M 次上游 HTTP 调用。

### 关键约束

- **file_id 账号绑定**：`_upload_image` 上传的 file_id 绑定到特定账号 token，跨账号无法复用
- **复用范围**：只能在**同一 token（账号）**的多次调用间复用
- **主要受益场景**：同账号重试（TLS 错误重试、连接超时重试、token 失效刷新后重试）

### 当前调用链

```
_generate_single_image (conversation.py:1359)
  → while True 循环，每次重新：
    → get_available_access_token (取 token)
    → OpenAIBackendAPI(access_token=token) (新建 backend)
    → stream_image_outputs(backend, request, index, total, total_deadline)
      → conversation_events(backend, ..., deadline)
        → backend.stream_conversation(..., timeout_secs)
          → _stream_picture_conversation(prompt, model, images, timeout_secs)
            → _upload_image(image) × 每张参考图  ← 重复上传点
            → _bootstrap
            → _get_chat_requirements
            → _prepare_image_conversation
            → _start_image_generation(prompt, requirements, conduit_token, model, references, timeout_secs)
    → backend.close() (finally 块，每次循环结束关闭)
```

### 修复方案

**核心思路**：在 `_generate_single_image` 层面维护 `token → references` 缓存，同账号重试时复用已上传的 references；修改调用链透传 `preloaded_references`，让 `_stream_picture_conversation` 跳过 upload 步骤。

### 缓存生命周期

- 缓存作用域：单个 `_generate_single_image` 调用（即单张图的生成+重试过程）
- 同 token 重试时复用：TLS 错误重试（MAX_TLS_RETRIES=3）、连接超时重试（MAX_CONN_TIMEOUT_RETRIES=3）、token 刷新后重试（如果 refreshed_token == token 则复用）
- 换 token 时不复用：新 token 重新上传并缓存
- `_generate_single_image` 返回后缓存自然释放（不跨图复用，因为并行模式每张图独立线程）

- 编辑模式生成单张图，模拟 TLS 错误触发重试，验证第二次循环不再调用 `_upload_image`（通过日志确认无重复 `uploading` 进度回调）
- 编辑模式生成 4 张图（并行），验证每张图的首次上传仍正常，同账号重试不重复上传
- 确认非编辑模式（文生图，无参考图）不受影响
